# KOVA Store 講師用資料

この資料は研修担当者向けです。店舗画面には脆弱性の説明や進行手順を載せていません。アプリは架空の顧客・商品・注文のみを扱い、サーバーから外部サービスへの通信や実決済は行いません。演習は自分で起動したこのインスタンスに限定してください。

## 対象範囲

KOVA Store は一般的な EC サイトに見えるよう、商品検索、レビュー、アカウント、カート、送料見積り、注文、会員概要、パスワード変更、特典ポイント、領収書共有、注文キャンセル、返品、外部連携トークン、スタッフ向け CSV、会員ウィジェット、リンクプレビューを備えています。ログインや CSRF 確認などはある程度実装されていますが、下表の業務処理には意図的な欠陥を残しています。「ログインしている」「画面上に入力欄がない」「トークンや有効期限がある」という事実だけでは、各処理の安全性は保証されないことを観察します。

| 観察する欠陥 | OWASP Top 10:2025 との対応 | 実際に起こること | 修正時の要点 |
| --- | --- | --- | --- |
| 注文の BOLA / IDOR | A01 Broken Access Control | 他の架空顧客の注文を、注文番号を指定して閲覧できる | 注文ごとにログイン者との所有関係をサーバーで確認する |
| プロフィールの権限フィールド一括更新 | A01 Broken Access Control、API Top 10:2023 API3 | 購入者が本来更新できない `role` を送信できる | 許可フィールドだけを明示的に更新し、権限変更を管理操作に分離する |
| 商品検索の SQL インジェクション | A05 Injection | 検索条件を変え、非公開商品の架空カナリアが結果に現れる | 検索条件をプレースホルダーに束縛し、公開範囲を常に強制する |
| レビューの保存型 XSS | A05 Injection | 投稿本文が商品画面で HTML として解釈される | レビューをテキストとして描画し、必要な書式だけを安全に許可する |
| 送料のクライアント側金額改ざん | A06 Insecure Design | 見積り結果を変えた注文をサーバーが受け入れ、合計額が下がる | サーバーが配送方法・宛先から送料を再計算して注文を確定する |
| ログイン試行制限の回避 | A07 Authentication Failures | 5回失敗すると制限されるが、利用者が送る `X-Real-IP` を変えると同じアカウントを再試行できる | 信頼済みプロキシ以外の転送ヘッダーを無視し、アカウント単位でも試行を制限する |
| パスワード変更コードの対象者不一致 | A07 Authentication Failures、A01 Broken Access Control | 自分の有効なコードを別の架空顧客のメールアドレスに対して使用できる | コードを発行対象のユーザーIDに結び、更新対象をそのIDから決める |
| 会員概要のキャッシュ混線 | A01 Broken Access Control | 先に閲覧した顧客の概要が、次に閲覧した別の顧客へ返る | 認証済み応答を共有キャッシュしないか、所有者を含む厳密なキーと失効条件を設ける |
| 特典ポイントの二重付与 | A06 Insecure Design | 同じトークンの同時確定が、一度限りの確認をすり抜けて二重に加算される | トークン消費と残高更新を同じ原子的なトランザクションで実施する |
| 領収書リンクの期限延長 | A04 Cryptographic Failures | 署名付きリンクの `expires` だけを変えると、同じ架空領収書を元の期限より後まで閲覧できる | 注文ID・期限・用途をまとめて署名し、許容期間も制限する |
| GET による注文キャンセル | A01 Broken Access Control（CSRF） | 所有者と状態の確認は通るが、外部ページからのトップレベル遷移でもキャンセルが成立する | 状態変更を POST/PATCH に移し、CSRF トークンと Fetch Metadata を確認する |
| 会員ウィジェットの広い CORS 許可 | A01 Broken Access Control | 同一ホストの別ポートを信用して認証済みの架空プロフィールを読ませる | 必要なオリジンをポート込みで列挙し、認証済みデータへの CORS 許可を最小にする |
| リンクプレビューの内部パス取得 | A01 Broken Access Control（SSRF） | 外部URLは拒否するが、内部専用パスをサーバー自身から取得して架空の仕入れメモを表示する | 取得対象を業務上必要なリソースに限定し、転送先でも権限を確認する |
| 連携トークンのスコープ無視 | A01 Broken Access Control | 商品閲覧専用の短命トークンが、架空の会員住所を返す API でも使える | すべての対象 API でトークンの用途・スコープ・所有者を検証する |
| 返品承認の順序回避 | A06 Insecure Design | 承認待ちの返品を確定 API に直接渡し、架空のポイントを受け取れる | 承認済みからのみ確定できる状態遷移をサーバー側で強制する |
| 注文 CSV の数式注入 | A05 Injection | CSV の引用符処理はあるが、注文者名の `=1+1` がセル先頭の数式として残る | CSV 構文のエスケープと、表計算ソフト向けのセル値無害化を別々に行う |
| 商品詳細の内部属性露出 | A01 Broken Access Control、API Top 10:2023 API3 | 一覧にはない架空の仕入れ原価・内部メモが詳細 JSON に含まれる | 公開レスポンスのプロパティを明示的に選ぶ |

分類は [OWASP Top 10:2025](https://top10.owasp.org/2025/0x00_2025-Introduction/) と [OWASP API Security Top 10:2023 API3](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/) を参照しています。2025年版の A01 には CSRF、CORS 設定不備、SSRF も含まれます。複数の分類に重なる欠陥もあり、この表は Top 10 の全10カテゴリを網羅するものではありません。依存パッケージを故意に古くしたり、外部URLへアクセスする実SSRF、実決済を組み込んだりはしていません。設計の参照先は [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)、[Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)、[Web Cache Security](https://cheatsheetseries.owasp.org/cheatsheets/Web_Cache_Security_Cheat_Sheet.html)、[Business Logic Security](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html)、[CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)、[HTML5 Security の CORS](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)、[SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)、[OAuth 2.0 のトークン権限](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html)、[WSTG のワークフロー回避](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/10-Business_Logic/06-Circumvention_of_Work_Flows/)、[CSV Injection](https://community.owasp.org/attacks/CSV_Injection)、[A04 Cryptographic Failures](https://top10.owasp.org/2025/A04_2025-Cryptographic_Failures/) です。

既にある防御も観察対象です。パスワードはソルト付きハッシュで保存し、ログイン時にセッションを更新します。Cookie は `HttpOnly` と `SameSite=Lax`、通常の状態変更 API には CSRF トークン確認があります。カートの数量、在庫、商品の価格はサーバー側で確認し、多くのデータベース処理では値を束縛しています。新しいフローでもログイン試行制限、ランダムな一回限りのコードと特典トークン、有効期限、ハッシュ保存、`Cache-Control: no-store`、所有者確認、署名、入力パス検証などを備えています。しかし、トークンのスコープ、返品の承認状態、CSV セルの意味、API の公開属性も個別に設計・確認する必要があります。XSS では `HttpOnly` によりCookie値を直接読むことは抑えられても、ページ上で実行されるコード自体は防げません。

SQL インジェクションの文字列連結は商品だけの使い捨てメモリ SQLite に限り、顧客・注文・セッションの表には接続しません。それでも結果のIDを通じて非公開の商品情報が漏れるため、実際の影響を確認できます。レビュー、注文、権限、パスワード、ポイント、キャンセル、返品の欠陥は架空データを保存する通常の業務処理にあり、演習後は初期化が必要です。パスワード変更コードは実際のメールに送らず、ログイン中の本人の画面にだけ表示します。領収書は架空の注文だけを返し、内部プレビューは固定の架空カナリアのみを返します。プレビューは外部ホスト、ファイル、任意の URL には到達しません。CSV は自分のテストデータをテキストとして確認し、表計算ソフトでは開かないでください。共有インスタンスを使う場合、他の参加者の操作でキャッシュ、ポイント、注文状態が変わるため、再現性のためには受講者ごとにインスタンスを分けてください。

## 準備

[README](../README.md) の手順で `docker compose up --build -d --wait` します。Mac からは `http://127.0.0.1:4327`、VMware NAT の Kali からは追加 Compose ファイルを使い、この環境では `http://192.168.180.1:4327` です。複数人で同じインスタンスを使うとレビューや注文が共有されます。演習の再現性が必要なら受講者ごとにインスタンスを分けてください。

初期の架空顧客は次の2人です。

| 顧客 | メール | パスワード | 初期注文 |
| --- | --- | --- | --- |
| 美緒 | `mio@kova.local` | `KovaDemo2026!` | `K-2026-1001` |
| 陽 | `haru@kova.local` | `KovaDemo2026!` | `K-2026-1002` |

画面操作の後で観察に使う場合は、ブラウザーの開発者ツールの Network タブで自分のリクエストを確認します。API に直接アクセスするときは、同じブラウザーのログイン済みセッションと CSRF トークンを使います。カナリア、注文、コード、ポイントはすべて演習用の架空データです。パスワード変更と会員概要の比較には、2人分のブラウザープロファイルを使うとセッションを分けやすくなります。新しい領収書リンクはリンクを知る人ならログインなしで開けるため、リンク自体を演習用の秘密として扱い、他の場所に貼らないでください。

## 観察例

### 1. 注文の所有者チェック

美緒でログインし、本人の注文 `K-2026-1001` を確認します。次に同じセッションのまま `GET /api/orders/K-2026-1002` を開きます。陽の注文が返る場合、認証は通っていても注文単位の認可が欠けています。修正するときは、IDの形式や推測しやすさに頼らず、取得クエリと返却前の両方で所有者を確認します。

### 2. 非公開商品の検索

通常の検索では公開商品だけが出ます。検索欄に `%') OR 1=1 -- ` を入力し、結果を確認します。非公開の「STUDIO 試作モデル」（社内限定）が一覧に現れ、検索 API の JSON では `description` に `CANARY-KOVA-PRODUCT-7` が含まれます。検索語が SQL の条件式として解釈されていることを確かめ、公開判定も含めて値を SQL 文字列に直接連結しない修正を考えます。

### 3. レビューの保存と再表示

商品ページから、無害な表示変更だけを行う HTML をレビュー本文として投稿します。例: `<img src=x onerror="document.title='KOVA REVIEW XSS'">`。保存後に商品ページを再表示し、ブラウザーのタイトルが変わるかを観察します。送信時の値が別の閲覧者の画面でもコードとして実行される点が保存型 XSS の影響です。実際の秘密情報の取得や外部送信は演習に不要です。

### 4. プロフィール更新とロール

通常のプロフィール画面では名前の変更だけを行い、Network タブで `PATCH /api/profile` を確認します。同じエンドポイントへ `{"role":"staff"}` を含む JSON を送信し、`GET /api/staff/overview` が使えるようになるかを確認します。入力欄がないフィールドでも HTTP クライアントから送れるため、サーバー側で更新対象を限定する必要があります。

### 5. 送料見積りと注文確定

`POST /api/shipping/quote` に `{"method":"standard","postalCode":"100-0001"}` を送ると通常の送料は480円です。Network タブで注文確定の `POST /api/checkout` を確認し、同じ商品の注文で `shippingFee` を `0` に変えた場合の合計額を比べます。改ざんした送料は注文に保存され、合計額とスタッフ向け売上にも反映されます。送料の見積りを先に呼んだことは、注文確定時の金額を信頼する根拠にはなりません。サーバーが配送条件をもとに再計算し、クライアント送信額は参照しない設計にします。

### 6. ログイン試行制限の識別子

美緒のメールアドレスに誤ったパスワードを5回送ると、同じ送信元からの次の試行は `429` と `Retry-After` を返します。続けて `X-Real-IP: 198.51.100.10` を付けて同じアカウントに試行すると、制限のカウンターが別扱いになることを確認します。これはクライアントが任意に書けるヘッダーを本人確認済みの送信元として扱った欠陥です。ヘッダーを変えた結果を、実在の第三者アカウントや大量の試行に拡張する必要はありません。修正時は信頼済みプロキシが設定した情報だけを採用し、アカウント単位の制限も設けます。

### 7. パスワード変更コードと対象アカウント

美緒でログインし、`POST /api/account/password-code` でコードを発行します。コードはランダムで、有効期限があり、保存時にはハッシュ化され、使用後は再利用できません。しかし `POST /api/account/password` の `email` に陽の架空アドレス、`code` に美緒のコードを指定すると、陽のパスワードが変更されます。別ブラウザープロファイルで陽の新しいパスワードを試すと影響を確認できます。演習後は初期化して初期パスワードに戻してください。修正時は入力されたメールアドレスで対象を選ばず、検証済みコードの発行先ユーザーIDを更新対象にします。

### 8. 会員概要とサーバー内部キャッシュ

美緒と陽を別々のブラウザープロファイルでログインさせます。美緒で `GET /api/account/overview` を開き、`X-Cache: MISS` と本人の概要を確認します。続けて陽で同じURLを開くと `X-Cache: HIT` になり、美緒の名前、メールアドレス、直近注文が表示されます。レスポンスに `Cache-Control: no-store` があっても、それはこのアプリ自身が保持する内部キャッシュのキーを正しくするものではありません。修正時は認証済みの概要を共有キャッシュしないか、ユーザーIDをキーに含め、認証と失効を一貫して適用します。

### 9. 特典トークンの同時確定

美緒で `POST /api/rewards/offer` により特典オファーを発行すると500ポイント用のランダムなトークンが返ります。他人のトークン、有効期限切れ、通常の順番での二度目の確定は拒否されます。同じトークンで `POST /api/rewards/claim` をほぼ同時に2本送ると、両方が使用前の状態を確認してしまい、残高が1000ポイントになることがあります。ポイントは架空の値で、支払いや外部の特典に連携しません。修正時はトークンの未使用確認・使用済みへの変更・残高加算を一つの原子的な処理で確定し、二重実行でも加算が一度だけになることを並行テストで確認します。

### 10. 領収書共有リンクの期限

美緒の注文 `K-2026-1001` について、ログイン済みセッションと CSRF トークンで `POST /api/orders/K-2026-1001/receipt-link` を呼び、返された相対 `url` を開きます。リンクには `expires`（Unix時刻のミリ秒）と16進数の `sig` があり、ログインなしでも架空の領収書を確認できます。同じ `sig` のまま `expires` だけを元の値より後、現在から1時間後など24時間以内に変えると、元の期限を超える閲覧が可能です。注文IDや署名自体を変えると拒否され、過去の期限も拒否されるので、検証処理が全くないわけではありません。原因は期限を署名の入力に含めていないことです。修正時は注文ID・期限・用途を一つのメッセージとして HMAC で署名し、サーバーが許す最長期間も独立に確認します。

### 11. GET による注文キャンセル

陽の初期注文 `K-2026-1002` は処理中です。陽のログイン済みブラウザーで `GET /api/orders/K-2026-1002/cancel` を開くと、CSRF トークンなしで注文が `cancelled` になります。別の顧客からの操作や処理中以外の注文は拒否されるため、所有者・状態の確認と CSRF の確認を区別できます。`SameSite=Lax` のCookieは外部ページからのトップレベル GET 遷移で送られ得るため、リンクを開かせるだけで状態変更が起こる設計は危険です。演習では `Sec-Fetch-Site: cross-site` を付けた自分のテストリクエストで境界を確認できます。修正時は GET を読み取り専用にし、POST/PATCH に CSRF トークンと Fetch Metadata の確認を適用します。再実行には注文状態のリセットが必要です。

### 12. 会員ウィジェットの CORS

美緒でログインし、`GET /api/account/widget` に `Origin: http://127.0.0.1:4328` など、アプリとホストが同じでポートが異なるオリジンを付けます。応答の `Access-Control-Allow-Origin` はその値になり、`Access-Control-Allow-Credentials: true` も付きます。JSON には美緒の架空のメールアドレスと住所が含まれます。無関係な外部ホストの Origin は許可されず、他の API でも同じ CORS ヘッダーは付きません。問題は「ローカルホストなら全ポートを信用できる」と見なした点です。同じ端末の別プロセスが開くページからも、このウィジェットの応答を読み取れる余地があります。修正時は必要なオリジンをスキーム・ホスト・ポートまで固定し、認証済みの情報を返す経路にだけ慎重に適用します。

### 13. 内部メモへのリンクプレビュー

ログイン後、`POST /api/links/preview` に `{"path":"/_media/notes"}` を送ると通常の架空メモがプレビューされます。外部URLは入力時に拒否されます。一般の API パスは取得後に応答形式が合わず、プレビューには表示されません。一方、`{"path":"/_internal/supplier-note"}` を送ると、サーバーが自分の内部専用URLを取得し、`summary` に `CANARY-KOVA-SUPPLIER` が現れます。VM 側などループバック以外から内部専用URLを直接開く操作は拒否されます。入力を相対パスに制限しても、許可した先に内部リソースが含まれればアクセス境界を越えます。修正時はプレビュー可能な業務リソースを明示的に列挙し、内部専用経路を除外します。HTTP 取得が必要な場合は転送先の再評価とネットワーク側の制限も併用します。この教材のプレビューは外部ネットワークへ接続しません。

### 14. 商品連携トークンの権限

美緒でログインし、CSRF トークン付きの `POST /api/integrations/tokens` で連携トークンを発行します。返却値は `catalog:read` のスコープと約15分の有効期限を持つランダムなトークンです。保存される値はトークンのハッシュです。Cookie を付けない別の HTTP クライアントから `Authorization: Bearer <発行したトークン>` を添えて `GET /api/integrations/catalog` を呼び、公開商品の一覧を確認します。同じヘッダーで `GET /api/integrations/account` を呼ぶと、美緒の架空のメールアドレスと住所も返ります。無効・期限切れのトークンは拒否されるため、認証や期限検証が丸ごと欠けているわけではありません。原因はアカウント経路でトークンの `catalog:read` スコープを確認していないことです。修正時は各経路で用途と必要なスコープを検査し、会員住所は適切に認可された主体にだけ返します。この教材のトークンは OAuth 認可サーバーや実在の外部サービスには接続しません。

### 15. 返品承認前のポイント確定

美緒の配達済み注文 `K-2026-1001` について `POST /api/orders/K-2026-1001/returns` で返品を申請し、`GET /api/orders/K-2026-1001/return` で `pending` を確認します。保存済みの演習状態でこの初期注文が配達済みでなくなっている場合は、スタッフ画面で配送を進めるか、配達済みになった別の自分の注文を使います。通常の流れではスタッフが承認してから、返品確定で架空の250ポイントが付与されます。一方、申請直後の `pending` の ID をそのまま `POST /api/returns/<返品ID>/settle` に渡しても、所有者の美緒が250ポイントを受け取れます。承認待ちを飛ばしても、二度目の確定は拒否されます。修正時は確定処理の中で保存済み状態が `approved` であることを確認し、状態変更と残高加算を一つの原子的な処理で行います。返品、注文、ポイントは研修用の架空データです。再実行にはデータの初期化が必要です。

### 16. スタッフ用 CSV の数式

自分のテスト注文の宛名に無害な算術式 `=1+1` を指定して購入します。スタッフ権限のアカウントから `GET /api/staff/orders/export.csv` を取得し、CSV を**テキストエディター**で開きます。`"=1+1"` と引用されていても、セル値は `=1+1` のままです。別の注文で宛名を `宛名, "研修"` にすると、カンマと引用符が CSV 構造として正しくエスケープされることも確認できます。CSV 構文が壊れていなくても、表計算ソフトでは先頭の `=` が数式として解釈される可能性があります。演習では表計算ソフトを起動せず、無害な文字列の残存だけ確認します。修正時は CSV の引用と数式として解釈される先頭文字の無害化を別々に適用し、実際に使う表計算ソフトと再保存時の挙動も確認します。スタッフ権限自体の確認はこの経路にあります。

### 17. 商品詳細 JSON の内部属性

ログイン前の `GET /api/products` では、商品に `supply` 属性はありません。公開商品の `GET /api/products/1` を開くと、画面には表示されない `product.supply.supplierCost` と `product.supply.internalNote` が JSON に含まれます。非公開商品は詳細URLでも拒否されるため、公開可否の判定とプロパティ単位の公開判定を区別できます。いずれも架空の仕入れ情報です。修正時は公開用の商品表現を詳細経路でも明示的に構築し、スタッフ専用属性を混ぜないようにします。[OWASP API3:2023](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/) はこの種の過剰な属性公開を扱っています。

## 観察後の整理

各演習で、入口の HTTP リクエスト、欠けたサーバー側の確認、返却または保存された結果を並べて記録します。その後、入力検証・認証・認可・出力処理・業務ルールを区別して、どの層で防ぐべきかを議論します。特に「CSRF があるからロール更新も安全」「画面に非公開商品がないから検索結果にもない」「一回限りのトークンがあるから同時実行も安全」「トークンにスコープがあるから全経路で制限される」といった推論を、実際のリクエストと照らします。

サイト内には進捗や正解表示を組み込んでいません。受講者が操作と観察を記録する形式を想定しています。
